# 멀티잡 · 공고별 타겟 개선 계획 (2026-07-28)

> 출발: 사장님 지적 **"공고 여러 개가 동시에 올라오면 공고마다 타겟군이 다를 텐데 그게 충분히 고려됐는지?"** → 확인 결과 **고려되지 않았음**.
> 3라운드 설문으로 정책을 확정하고, 3갈래 설계 조사(멀티잡 응대 · 노출 축 · 양측 UI)로 구현 순서를 잡았다.

## 확정된 정책 (설문 2026-07-28)

| 축 | 결정 |
|---|---|
| 노출 축 | **시군구(구 단위) · 희망 시간대(평일/주말×오전/오후) · 집결지 거리 반경(km)** 전부 추가 + 실무자 자유 필터 |

## 배치 순서 (위험 낮은 → 높은)

### M1 — 안전판 + 자유 필터 동선 + 시군구 축 ✅ (#107 · M1b PR)
1. ✅ **공고 결속 안전판** — `lib/agent/candidate-target.ts`로 대상 후보 판정 단일화. 지금은 공고 미선택 시 엉뚱한 공고의 AI가 꺼지고 'AI 재개'가 400으로 실패한다. 활성 후보 1개면 현재와 100% 동일 동작.
2. ✅ **파이프라인 '이 조건으로 고른 사람만 노출'** (M1b) — 버튼 문구(`이 명단에게만 노출`)·조건 요약 한 줄·원클릭(공고를 지정 노출로 전환 + 명단 include). 저장된 규칙이 있으면 '규칙 지우고 N명만' vs '규칙 두고 N명 추가' 2택(규칙 소거를 조용히 하지 않는다). **축을 늘리지 않고 자유도를 얻는 핵심 단계.**
   - 구현 중 드러난 것 3개(계획에 없던 것):
     - **전체 노출 공고에 남아 있는 예전 규칙** — 노출 방식만 전환하면 고르지 않은 '규칙 해당 인원'에게도 함께 보인다(조용한 확대). → 규칙이 있으면 2택 없이는 진행 불가(화면 disabled + 서버 400 `rule_action_required`).
     - **노출 게이팅은 후보 여부를 보지 않는다**(`isExposed`만 본다) → 전환·규칙 삭제로 이야기 중인 공고가 지원자 화면에서 사라진다. 이미 연결된 인원(관심·후보, 이탈만 제외)을 자동 include로 남긴다. 순서는 **자동 보호 insert → 명단 upsert → 전환 → 규칙 삭제**(첫 실패 시 공고가 하나도 안 바뀐 상태).
     - **선택 ≠ 조건 결과** — 조건 밖에서 직접 체크한 인원 수를 모달에 따로 표시(조건 요약이 거짓이 되지 않게).
   - 신규: `GET /api/admin/exposure/impact?job_ids=` (공고별 현황 배치 조회 — 공고마다 인재풀 전량 로드를 반복하지 않게) · `lib/exposure.ts describeRule()`(지울 규칙을 사람 말로).
   - 적대적 게이트 2회(1차 6렌즈 40건 → 25건 확인 / 재검증 7렌즈)에서 잡아 함께 고친 것:
     - **노출 축소·후보 생성 경로가 여러 개** — 파이프라인 일괄 배정 · 공고 수정 모달 저장 · 인박스 실공고 등록 · 공고 후보 추가. 보호를 `lib/exposure`(`gatherExposureProtectTargets`/`writeExposureProtectRows`/`ensureExposureIncludeForLinked`) 한 곳으로 모으고 네 경로 전부에 배선했다. **경로 하나만 닫으면 반드시 뚫린다**가 이 배치의 교훈.
     - **lost update** — 수정 모달이 열던 시점 노출 값을 무조건 PATCH에 실어, 급여만 고친 저장이 방금 좁힌 노출을 되돌리고 '되돌릴 수 없다'며 지운 규칙을 부활시켰다. 노출을 만졌을 때만 전송 + 만졌으면 서버 값 재확인.
     - **캠페인 답장 자동 편입이 거리 최근접으로 추측** — 공고가 여럿이면 안내받은 공고가 아닌 다른 라인으로 편입돼 AI가 엉뚱한 공고를 응대했다. 근거(관심 클릭 → 안내 문자 → 활성 1개)만 쓰도록 재정렬.
     - **약속·안내가 조용히 깨지는 경로 2개** — `대기자에게 안내`의 명단 밖 제외 수 미표시, 명단 밖 답장자의 무응답(AI·Slack 둘 다).

### M1b 이후로 의도적으로 넘긴 것 (게이트가 비차단으로 판정)

| 항목 | 지금 상태 | 왜 넘겼나 |
|---|---|---|
| 규칙을 **넓히는** 저장도 보호 대상이 되어 include가 생김 | 과다 보호 | 방향이 안전(사람이 공고를 잃지 않음). 정확히 하려면 '변경 후 규칙에 안 맞는 사람만' 계산해야 하는데, 조회 실패 시 저장이 막히는 새 실패 모드가 생긴다. 규칙 사용이 늘면 재검토 |
| 같은 공고 재안내(8일 후)에서 auto_linked pin이 노출 필터를 통과시켜 중복 1통 가능 | 열림 | 7일 피로도 필터가 대부분 막고, 재안내는 매니저가 의도적으로 누르는 동작 |

| 자유 본문으로 공고를 알린 수신자는 보호 밖 | 구조적 한계 | 그 문자에 `job_id`가 없어 어느 공고를 알렸는지 알 수 없다. `대기자에게 안내`(purpose=new_job)만 보호 가능 |

| `abort` 후보를 후보 추가 훅은 포함(축소 보호는 제외) | 과다 보호 | 매니저가 방금 다시 추가한 사람이라 노출을 주는 쪽이 맞다 |
3. ✅ **시군구 축** — `sido`와 동형. `matchesTextAxis(allow, v)`로 빈 값은 `'미확인'` 선택 시에만 통과. 옵션 API가 `sigungu` distinct + 시도별 그룹·건수 제공. 동명이구(중구·서구)는 **정확 일치 유지** + 시도 그룹 헤더로 구분.

### M2 — 슬롯 어휘 단일화 + 희망 시간대 축 ✅
4. ✅ `lib/admin/types.applicantAvailableSlots()` 신설 — 파이프라인 조건 바와 노출 규칙이 **한 함수**를 쓴다. 라벨도 `SLOT_LABEL` 하나로(예전엔 `평일오전`/`평일 오전`/`평일 · 오전` 3종). **`matchesSlot`은 건드리지 않았다** — 그건 비마트 슬롯 보드(지점×슬롯 확정/대기 집계, `confirmed_slot`과 짝) 전용이고 '이 사람이 언제 가능한가'와 다른 질문이다(주석으로 명시).
5. ✅ 시간대 축 추가 — 판정 순서 `available_slots`(자기 신고, 신설 컬럼) → `work_hours`(폼 토큰 → 자유 입력 파서). **`confirmed_slot`은 쓰지 않는다**(비마트 전용 개념 — 사장님 확인). 현 데이터 30명 전원이 폼 토큰도 갖고 있어 제외해도 변화 0.
   - **파서 실측(645명 전량 검증)**: 폼 토큰 250 + 파서 156 = **슬롯 확정 406명(63%)** · 미확인 239명. 미확인은 값이 `~` 한 글자(206) + 요일만·야간·새벽·범위 없는 값(33)으로, **파서로는 채울 수 없는 값**임을 데이터로 확인.
   - 파서 규칙: '평일'·'주말' 단어를 먼저 반영하고 지운다(안 지우면 '평일'의 '일'이 일요일로 읽힌다) · 요일→평일/주말(결정적) · `9:00~6:00` 같은 12시간제 종료는 +12 보정 · **12시 기준 앞뒤로 각 2시간 이상 근무하면 그 슬롯**(짧은 근무는 더 긴 쪽) · **야간(18시 이후 시작)·새벽(9시 전 종료)·시작=종료·보정 후에도 뒤집힌 범위는 미확인**(추측 금지).
     - 게이트에서 버린 두 방식: 시작 시각만 보기 → `9:00~13:00`이 오후 라인에도 걸림(27명) / 폼 창 겹침(09~14·12~17) → `13:00~18:00`이 '오전', `6:00~10:00`이 '미확인'으로 뒤집힘.
   - localStorage 저장 세그먼트 하위호환: 읽기 시 `replace(/\s/g,'')`로 레거시 라벨 흡수.
   - 판정 재료(`work_hours`·`available_slots`)를 `ExposureApplicant`에 **필수 필드**로 넣어, 배선을 빠뜨린 판정 지점이 컴파일 오류로 드러나게 했다(5곳 전부 배선 확인 — 차량·시군구 축에서 겪은 '조용한 전원 탈락' 재발 방지).
   - 게이트 재검증(유실된 18건 지적 전문을 회수해 직접 판정)에서 추가로 고친 것: **폼 재제출·매니저 수정이 오래된 AI 값에 지던 문제**(work_hours를 새로 받으면 available_slots를 비운다) · **조건 바에 '미확인' 칩 없음**(239명을 수동 명단으로 만들 수 없었다) · **'매일'·'평일'의 '일'이 주말로 읽히던 오독** · **자유 입력의 '오후' 표기를 안 읽어 `오후 1:30~5:30`이 새벽으로 뒤집히던 문제** · 미확인 칩 설명이 partial 구성을 잘못 단정 · 규칙 미리보기 숫자가 '노출 기준 전체'임을 밝히지 않은 것 · 마이그레이션 주석과 코드 불일치(빈 배열 의미).
6. ✅ 미확인 채우기 — **재확인 문자는 보내지 않는다**(맞춤링크를 넣으면 `campaign` 태깅으로 24시간 교차 가드가 발사 고지를 막는다). 대신 **AI 스크리닝이 대화 중 곁들여 확인**하고 `available_slots`로 승격한다. **필수 아님**(advance 조건에 넣지 않음 — 사장님 결정): 답이 애매하면 비우고 그냥 진행, 추측 금지, 되묻지 않음.

### M3 — 집결지 거리 반경 축 ✅
7. ✅ **거리 공식 단일화**(동작 변화 0) — `lib/geo.ts` 신설. 같은 질문에 세 답이 있었다: pool GET의 사설 `distKm`(집결지만) · announce-targets의 인라인 `min(집결지, 경유지)` · 후보 목록의 또 다른 인라인. 실측으로 공고 33(용산·한남)은 집결지↔경유지가 13.8km 떨어져 **15km 대상이 190명 ↔ 296명**, 10km는 **99명 ↔ 181명**으로 갈렸다. 네 곳을 `distanceToJobKm` 하나로 모으고 `EXPOSURE_JOB_GEO_COLUMNS`로 select를 통일했다.
8. ✅ **기준점을 공고가 정한다** — `jobs.distance_basis`('pickup' | 'nearest', 기본 `nearest`) + 수정 모달 선택 UI(사장님 결정: 공고마다 고를 수 있게). 기본값을 `nearest`로 둔 이유: '대기자에게 안내'의 15km 조건 매칭이 이미 그 기준이라, 기본을 바꾸면 기존 대상이 조용히 좁아진다(공고 33: 296→190).
9. ✅ **반경 축 판정** — `radiusKm`(1~100 정수) + `radiusIncludeUnknown`. 판정 재료(`lat`·`lng`)를 `ExposureApplicant` **필수 필드**로, 공고를 `ExposureContext`로 넘기게 해서 배선 누락이 컴파일 오류로 드러나게 했다(8곳 전부 배선 — 판정 5곳 + 관리자 미리보기 3곳).
   - 좌표 없는 186명은 **지오코딩으로 채울 수 없다**(실측: 주소가 `미지정` 106 · `미확인` 74 · `.`/`?`/`데이터없음` 6 — 전부 플레이스홀더). `주소를 몰라 거리를 못 재는 분도 포함` 체크박스로만 넣는다.
10. ✅ **쓰기 시점 가드** — 좌표 없는 공고에 반경 규칙을 저장하면 아무에게도 안 보이므로 POST/PATCH 400. **노출을 만지지 않고 집결지 주소만 지우는 저장에도 걸린다**(그때 공고가 조용히 사라진다 — 가드를 노출 블록 안에 두면 새는 경로였다).
11. ✅ 미리보기 — 공고를 함께 넘겨 그 공고 기준으로 계산하고, 기준점이 없으면 **'0명'이 아니라 '계산 불가'**로 표시(조건이 까다로운 줄 오해하지 않게) + 좌표 미확인 인원 수 표시. 수정 모달에서는 **방금 고른(아직 저장 안 한) 거리 기준**으로 계산한다 — 저장된 기준으로 재면 같은 모달에서 296명을 보고 190명을 저장하게 된다.
12. ✅ **게이트가 잡은 것(확정 13건 + 유실 30건 회수 판정)**:
   - [차단] interest·notify가 판정 재료(지원자 좌표·공고 기준점)를 select하지 않아 **반경 규칙 대상 전원이 '마감된 공고예요'로 튕겼다** — 카드는 보이는데 클릭만 400, 매니저 쪽엔 아무 신호도 없다. `as unknown as GeoJob` 캐스트가 컴파일 안전망을 무력화한 것이 원인 — select 문자열은 타입이 못 지킨다.
   - [차단] engage 캠페인 답장 게이트가 distance_basis를 안 읽어 'pickup' 기준 공고를 nearest(넓은 쪽)로 판정 — 본인 링크엔 없는 공고로 자동 편입될 수 있었다.
   - [차단] 지원자 카드 '집에서 약 N km'가 min(집결지, 경유지)로 바뀌어 통근 거리를 최대 13.8km 짧게 보여줬다 → **카드 거리는 항상 집결지(통근) 기준**으로 고정(판정 기준과 다른 질문).
   - [차단] 복제가 반경 규칙을 보이지 않게 실어 등록 가드에 걸려 **등록 자체가 막혔다**(회복 UI 없음) → 복제 시 반경은 싣지 않고 안내 토스트.
   - 공고 기준점 없음 + '주소 미확인 포함' = fail-open(전원 통과) → 기준점 없으면 포함 여부와 무관하게 차단(fail-closed). 오설정 방지는 쓰기 가드가, 방어는 판정이.
   - 전체 노출 공고에 남은 반경 규칙이 주소 수정을 400으로 막았다(규칙 편집기는 targeted에서만 열려 지울 UI가 없는 막다른 길) → 가드를 '지정 노출일 때만'으로 축소 + 파이프라인 원클릭 전환이 그 상태를 우회 생성하지 않게 전환 쪽에도 같은 가드.
   - 거리 기준·좌표 변경은 노출 필드를 안 만져도 반경 대상을 줄인다(296→190) → M1b 보호(연결 인원 pin)를 같은 조건으로 확장.
   - 지오코딩 실패 시 옛 좌표가 남아 규칙이 예전 집결지를 겨냥했다 → 주소가 바뀌었는데 좌표를 못 얻으면 좌표를 비운다(주소·좌표가 다른 곳을 가리키는 거짓 상태 금지).
   - 파이프라인 '공고 근거리순'이 네 번째 사설 공식(min 하드코딩)이었다 → lib/geo + 공고 기준으로 교체.
   - normalizeRule이 0.3km를 0으로 반올림해 '조건인 척하는 no-op' 저장 → 반올림 후 1~100 검증.

### M4 — 지원자 화면
9. **fit 판정을 서버로** — `lib/pool-fit.ts`. 재료가 클라에 없고(좌표는 PII), 판정 소스를 3개로 늘리면 안 되며, 순서를 서버가 확정해야 한다(클라는 백그라운드 재정렬 금지 규칙이 있다).
10. **맞는 자리 위 + 나머지 접기** — 카드 JSX는 그대로 추출만. `warn`(요건 어긋남 확정)만 접고 `unknown`(정보 없음)은 위 그룹에. **카드는 절대 숨기지 않는다**(fit은 순서·접기 전용, 노출 게이팅과 분리).
11. **카드 상황 배지** — `lib/pool-status.ts`. 금지어 주석 필수: `in_progress`는 '이 자리로 이야기 중', 보류·종료 건에는 연락 약속 문구 제거.

### M5 — 실무자 화면
12. 목록 카드에 **관심 공고 배지**(일괄 조회 API). **목록 배지 집합 = 선택 시 탭 집합**이어야 한다.
13. '사람 확인 필요' 탭을 **한 사람 = 한 카드**로 그룹핑(사람이 공고 수만큼 불어나는 실제 지점).
14. 선택 상태 통합(`{applicantId, wantJobId}`) + **공고 탭 상시 노출** + 배지 클릭으로 전환.

### M6 — 멀티잡 병행 응대 (가장 무거움)
15. **인입 라우팅 단일화** — 지금 3곳이 서로 다른 기준(웹훅=직전 outbound 앵커 / sweeper·draft=최신 후보). `lib/agent/inbound-routing.ts`로 통일하고 앵커에서 **캠페인 발송을 제외**한다(그게 없으면 7개 동시 발사 시 모든 답장이 '마지막 발송 공고'로 몰린다). 텍스트 명시 매칭은 **정확히 1건일 때만** 채택, 2건 이상은 되묻기(24h 내 2회면 pause).
16. **다른 공고 정보 블록 확장 + 병행 규칙** — 블록에 답할 수 있는 값을 싣고 **빈 항목을 항목명으로 열거**한다(빈칸을 숨기면 모델이 현재 공고 값으로 메운다). 결정적 백스톱: tool에 `answered_other_job_id`를 자기신고받아 그 공고가 비어 있으면 transition을 pause로 강등.
17. **공통 답변 사람 단위 승격** — 값은 기존 컬럼 재사용(`own_vehicle`·`vehicle_type`·`self_ownership`·`available_date`), 신설은 확인 메타 `applicants.profile_confirmed JSONB`뿐. **긍정 방향만 승격**('있음→없음' 강등은 pause).
18. **`current_job_id` 잠금 해제** — 발송 중복 가드를 다른 기준으로 교체하고 포인터는 '확정 결속'으로만 축소. **같은 배포에 확정 대상 공고 필수화**(서버 400)를 넣어야 확정 후속(만남장소·첫날)이 대상을 잃지 않는다.
19. **1지망 한 자리** 컬럼 + 매니저 수동 변경 + 양측 배지 → 20. 에이전트 신호 감지로 자동 갱신 → 21. 잔여 포인터 데이터 위생.

## 반드시 지킬 불변식

- **판정은 한 곳에만** — 차량(`normalizeVehicleOwned`)·슬롯(`applicantAvailableSlots`)·대상 후보(`resolveCandidateTarget`)·인입 라우팅(`pickCandidateForInbound`). 이 코드베이스는 "같은 개념 두 공식"으로 두 번 사고를 냈다.
- **fail-closed 방향** — 판정 재료가 없으면 노출하지 않는다. 단 '미확인'을 매니저가 명시적으로 고를 수 있게 해서 조용한 탈락은 없앤다.
- **fit ≠ 노출** — 맞지 않는 자리도 보이게 두고 순서·접기로만 다룬다(차량이 새로 생긴 분을 막지 않는다).
- **확정 뉘앙스 금지** — 상황 배지·병행 응대 문구 어디에도 배정·확정 암시를 넣지 않는다.
- **보조 집계 금지** — 충원율에 `confirmed_at` 같은 두 번째 기준을 추가하지 않는다(이미 두 번 겪은 오탐 원인). 신규 확정부터 포인터가 반드시 채워지게 하는 방향으로만 고친다.

## 남는 위험

1. **M6는 실전 첫 운영에서 검증되지 않은 코드가 돈다** — 킬스위치를 첫날 `코파일럿(초안만)`으로 두고 관찰하는 것을 전제로 한다.
2. `jobs.slot`이 자유 텍스트 80자라 공고 쪽 시간대 판정은 오탐 여지가 있다 → 명시 토큰만 판정, 그 외 `unknown`.
3. 좌표 미확인 186명은 반경 규칙에서 항상 빠진다(또는 '미확인 포함'을 켜야 들어온다) → 지오코딩 백필이 선행 과제.
